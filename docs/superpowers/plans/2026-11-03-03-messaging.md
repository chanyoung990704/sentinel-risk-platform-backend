# 03 실제 Outbox 전달·격리·복구 구현 계획

> **실행자:** `superpowers:executing-plans`로 진행한다. K01/K01P는 택일이다.

**Goal:** DB에 수락된 요청을 선택한 발행기로 실제 Kafka에 전달하고 중단/재전달/잘못된 메시지를 추적한다.

**Architecture:** 불변 Outbox, CDC 우선 또는 delivery lease 폴링, DB 수신 커밋 후 ACK, 격리 원문+DLT Outbox를 사용한다.

**Tech Stack:** E03에서 잠근 Kafka/Connect/Debezium 또는 Spring scheduling/JDBC, 기존 계열 Spring Kafka.

**Spec / Global Constraints:** [설계](../specs/2026-11-02-portfolio-reliability-design.md), [공통 계약](2026-11-03-execution-contracts.md), [실행 순서](2026-11-03-execution-index.md).

**Review Focus:** CDC INSERT와 폴링의 wire 계약 차이, ACK 전에 DB를 커밋하지 않는 실수, DLT 장애 시 원문 유실, 관리 재개와 단순 재전달의 혼동.

## K02. 실제 소비자 ACK·durable 격리와 DLT

**의존:** 선택한 K01 또는 K01P,R02,R06

**Files:** 생성 V35__create_message_quarantine.sql 및 H2 대응(번호 순서 적용); J/messaging/consumer/CustomReportKafkaConsumer.java, CustomReportKafkaConfig.java; J/messaging/quarantine/QuarantineService.java, QuarantineReplayCommand.java; scripts/reliability/replay-quarantine.ps1; T/messaging/ReportConsumerAckIntegrationTest.java, ReportQuarantineIntegrationTest.java. 기존 AiJobKafkaConsumer는 일반 보고서 경로로 유지한다.

**Interfaces:** onRequest(ConsumerRecord<byte[],byte[]>,Acknowledgment); quarantine(record,error)->QuarantineId; repairAndReplay(actor,quarantineId,correctionCommandId,targetRequestId,reason)->newEventId 또는 기존 job 관리 재개 안내. 원문 ID가 신뢰 불가능할 수 있어 명시 대상과 DB 고정 입력으로 재구성한다.

- [x] **1 — 실패 시험 작성:** inbox DB commit 직전/직후와 ACK 직전에 barrier를 둔다. DB outage에서 offset이 앞으로 가지 않음, 잘못된 JSON/스키마/DB 입력 hash 불일치, 동일 offset 재전달, DLT broker outage, 이미 FAILED job이 존재하는 DLT 재처리를 시험한다.

  기대 assertion: `assertThat(committedOffsetBeforeDbCommit).isEqualTo(previousOffset); assertThat(quarantineRowsForOffset).hasSize(1); assertThat(dltOutboxRowsForQuarantine).hasSize(1)`
- [x] **2 — red 확인:** Ubuntu native에서 `./gradlew realInfraTest --tests "*ReportConsumerAckIntegrationTest" --tests "*ReportQuarantineIntegrationTest" --console=plain`. 실제 실패 지점을 기록하고 환경 부재와 구분한다.
- [x] **3 — 최소 구현:** 새 consumer는 auto.commit=false, record listener, MANUAL_IMMEDIATE ACK를 사용하고 inbox service의 실제 transaction 반환 뒤 ACK한다. 장시간 AI는 호출하지 않는다. 일시 DB 장애는 ACK 없이 retry/컨테이너 일시정지로 처리하고 무한 tight loop를 피한다. poison record는 제한된 원문을 격리 journal+DLT Outbox에 원자 저장한 뒤 ACK할 수 있다. Kafka offset ACK 후에도 원문은 DB에 남기며 DLT 전달 확인 전 삭제하지 않는다. 기존 FAILED job은 R06으로만 재개하고, job이 없는 수정 replay는 새 eventId+원본 참조와 입력 검증을 사용한다.
- [x] **4 — green/회귀:** 같은 명령으로 DB와 offset gap, DLT 전송 실패, 관리 재개/메시지 repair의 구분이 통과해야 한다. 임의 payload의 requestId만 보고 진짜 요청을 FAILED로 바꾸지 않는다.
- [x] **5 — 증거/검토:** topic/partition/offset·eventId·DB 커밋·ACK·job/result 대조와 재개 시간을 run 원자료에 저장한다.
