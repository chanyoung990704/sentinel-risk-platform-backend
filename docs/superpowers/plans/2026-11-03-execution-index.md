# SENTINEL 애플리케이션 구현·측정 실행 계획

> **실행자 지침:** 구현을 시작할 때 `superpowers:executing-plans`를 적용한다. 사용자가 별도로 병렬 실행을 선택한 경우에만 `superpowers:subagent-driven-development`를 적용한다. 아래 체크박스와 하위 계획의 실패 재현→구현→검증 순서를 따른다.

**Goal:** 맞춤 보고서 한 흐름, 재시작 가능한 실제 데이터 적재, 성능 개선과 장애 복구를 구현하고 재현 가능한 수치를 얻는다.

**Architecture:** MySQL 요청+Outbox 원자 저장, CDC 우선/불가 시 단일 폴링 릴레이, Inbox+DB 작업 원장, DB 트랜잭션 밖의 외부 작업, 요청별 파일 확정, DB를 기준으로 재구성 가능한 Redis 조회 계층을 사용한다.

**Tech Stack:** 기존 Java 21 / Spring Boot 3.5.9 / Gradle 8.14.3 / JPA·QueryDSL·Flyway·Spring Batch / MySQL·Redis·Spring Kafka. 컨테이너·커넥터의 정확한 버전과 digest는 E02/E03에서 실제 검증 후 잠근다. 라이브러리의 무조건 최신 버전 업그레이드는 하지 않는다.

**Spec:** [승인된 방향의 설계](../specs/2026-11-02-portfolio-reliability-design.md) / [상위 로드맵](2026-11-02-portfolio-reliability-roadmap.md)

**상태:** 2026-11-12 기준 E01~E03/D01~D04/M01~M04/R01~R07/K01~K03 구현·승인범위시험을완료했다. R07최종브라우저13/Python71·Java591통과/기존15비활성(이후Java입력동일)·build·149976활성행지문유지를확인했다. M03 V2 15회4756완료, M04 ABBA12회응답불일치0/기본cache-off유지판정으로G2/G3증거를확보했다. 독립Important3는한번RED→GREEN보강했고Minor1은문서화보류했다. 시험9622PDF는복사보관했고사용자명시승인뒤시험계정20/9622보고서·PDF/소유확인격리714를정리했다(미확인828보존). 다음M05~M07은미착수이며원천사실전체/실제AI품질/배포는검증범위밖이다. 하위체크와원자료를근거로이전M02개선율과섞지않는다.

## Global Constraints

- 백엔드 B=`C:/sandbox/02_개발/sentinel-risk-platform-backend`, 자료 A=`C:/sandbox/02_개발/KT_AIVLE_School_8기_AI트랙/06_빅프로젝트_SENTINEL/01_SENTINEL_개발원본_내부경로유지`, 프런트 F=`A/front/front`.
- 자료 원본·기존 PC MySQL·비밀 파일·사용자 변경을 보존한다. 구현 전에 격리된 실행 위치와 현재 소스 snapshot/변경 목록을 확보한다. head SHA만으로 dirty 소스의 버전을 설명하지 않는다.
- 공개 배포·실제 AI 품질·다중 브로커 HA·연도별 대량 적재·전체 UI 개편은 필수 범위 밖이다.
- CDC는 E03에서 우선 검증하며 선택된 K01 또는 K01P 하나만 구현한다. 일시 장애 때 두 릴레이를 동시에 켜지 않는다.
- Redis write-behind는 조건부 후속이다. 필수 구현은 측정으로 선택한 한 조회의 cache-aside와 상태 복구이다.
- API/소유권/업무 키/상태/기본값은 [공통 실행 계약](2026-11-03-execution-contracts.md)을 따른다. 보장 범위를 넓히는 변경은 해당 계약과 시험을 함께 갱신한다.
- 실패를 먼저 재현하고 최소 구현 후 확인한다. 단위·MySQL 통합·실제 Kafka/Redis·프로세스 종료 시험의 증거를 구분한다. 비활성 테스트를 삭제하거나 통합 테스트를 제외해 전체 통과로 만들지 않는다.
- migration 번호 V28~V35는 현재 실행 계약의 순서다. D03의 평균 출처 격리에 V30을 사용해 아직 없는 인덱스/요청/jobs/polling/quarantine을 V31~V35로 재배정했다. 착수 시 다른 migration이 추가됐으면 가장 큰 숫자 다음으로 일괄 재배정한다. 적용된 migration은 수정하지 않는다.
- 각 작업은 테스트/구현/문서 변경 범위를 함께 검토한 뒤 독립된 변경 묶음으로 남긴다. 커밋을 수행할 때만 저장소 규칙의 영어 메시지를 사용하며, 현재 계획 작성 단계에서는 커밋/배포하지 않는다.

## Review Focus

## 실제 실행 순서와 통과 지점

2026-11-12 현재 R07/M03/M04까지완료했다. **G2는실제브라우저요청~모의PDF/본인다운로드와K03강제종료복구근거로통과, G3는동일조건캐시비교/기본off판정까지완료**했다. 성능개선성공/운영SLA로바꾸어표현하지않는다. [화면·캐시조건](../../runtime/browser-and-measurement.md)과결과 (로컬 자료·Git 제외: `../../results/browser-and-cache.md`)에실측·실패·보강·한계를정리했다. 사용자승인뒤시험데이터정리도완료했으며원자료/보관본/미확인격리828은보존했다.

1. E01 → E02 → E03: 환경과 CDC 채택 여부를 확정한다. Docker/권한/자원이 준비되지 않으면 설치 계획과 미완료를 보고하며 실제 인프라 시험 통과로 간주하지 않는다.
2. D01 → D02 → D03 → D04: 원본을 보존하며 데이터셋을 검증·활성화한다. **G1:** 재적재/재개/활성화의 값·키 대조 통과.
3. M01 → M02: 계측기를 검증하고 현재 조회의 MySQL 기준선과 한 가지 SQL 개선 실험을 확보한다. 이때 맞춤 요청 상태의 수치는 아직 측정하지 않는다.
4. R01 → R02 → R03 → R04 → R05 → R06: DB 경계별 기능을 작은 시험으로 완성한다.
5. 선택한 K01 또는 K01P → K02 → K03 → R07: 실제 Kafka와 브라우저 흐름을 연결한다. **G2:** 추가 요청 입력→접수→모의 AI 수신→PDF→본인 다운로드, 중복/강제 종료 복구 통과.
6. M03 → M04: 새 요청/상태 조회의 cache-off 기준선을 확보한 다음 캐시를 적용하고 같은 조건으로 비교한다. **G3:** 개선 효과와 오류/정합성 비용을 함께 보고.
7. M05 → M06 → M07: 운영·복구 절차와 전체 장애 매트릭스를 재확인하고 결과물을 정리한다. 각 작업에서 이미 실패 시험을 수행하며 이 단계에서 처음 시험하지 않는다. **G4:** 대표 3사례의 원자료/재현 명령/한계가 연결됨.

2026-11-13 다음 실행 단위는 [M05 범위 문서](2026-11-13-m05-scope.md)로 한정한다. 기동·종료·한도·정지checkpoint/분리복원과관련회귀/증거정리까지이며M06전체행렬/M07최종편집은후속이다. 범위문서작성만완료했고구현·인프라실행은아직시작하지않았다.

## 실행 규칙

- 하위 문서의 `B`, `F`, `J`, `T` 경로 약어와 테스트 task는 공통 계약에 정의했다. 제시한 명령은 관련 작업에서 파일/task를 만든 뒤 사용한다.
- G1/G2가 실패하면 성능 측정으로 넘어가지 않는다. 응답이 빠르더라도 데이터/업무 효과가 틀린 실행은 성능 성과에서 제외한다.
- 실험 반복 중 설정/이미지/데이터/hash가 달라지면 다른 run family로 기록한다. 기존 결과 파일을 덮지 않는다.
- 개선 전 원자료는 코드/설정 변경 전에 저장한다. 이전 수치나 설계상의 기대값을 새 실험 결과로 옮겨 적지 않는다.
- 각 작업 종료 시 변경 파일·시험 명령·실제 결과·건너뜀 이유·다음 의존 작업을 로그에 남긴다. 실패 상태를 숨기지 않는다.
