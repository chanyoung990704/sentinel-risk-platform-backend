# 다음 실행 범위: M05 운영 절차와 정지 시점 복원 검증

2026-11-13. 사용자 요청에 따라 다음 작업의 경계를 정리했다. 기존 승인 설계와 M05를 구체화한 범위 문서이며 구현·실험은 아직 시작하지 않았다. M06/M07까지 한 번에 확대하지 않는다.

## 현재 출발점

- R07 화면/JWT~모의PDF, M03 기준선, M04 상태 캐시/장애/전후 비교와 독립 검토 보강을 완료했다. 상태 캐시는 기본 off를 유지한다.
- 이전 시험 계정20/보고서·PDF9622/소유 확인 격리714와 종속 기록은 사용자 승인으로 정리했다. 원자료·PDF ZIP·재무149976행·소유 미확인 격리828/연결 Outbox828은 보존돼 있다.
- 워커의 시작/claim 중단/종료와 API·워커 readiness 코드가 이미 있다. 새로 전부 만들지 않고 실제 경계 시험에서 확인된 문제만 수정한다.
- 애플리케이션·Gradle·Docker·시험은 WSL2 Ubuntu에서 실행하고, Windows 래퍼는 Ubuntu 실행으로 연결한다.

## 상세 경계

- 과부하 시험은 기존 프로토콜의 GLOBAL=5/USER=3·모의 응답 barrier·고유100건과 동일 키100건을 분리한다. 고유 요청 모두를 수락해야 한다는 시험이 아니다. 수락 집합과 429/503 거부 집합을 따로 대조하며 수락된 요청은 삭제하지 않는다.
- 정상 복구 사례는 기본 수락 집합100건, 특정 commit/종료 경계는 대상1건으로 위치를 증명한다. 각 시나리오3회, 정상 완료 관찰 한도180초를 기준으로 하되 실행 전 case별 입력/기대값을 manifest로 고정한다. 한도 초과는 미완료로 기록한다.
- checkpoint는 실행 중인 DB/파일을 임의로 복사한 것을 의미하지 않는다. 신규 접수/worker 쓰기를 중단하고 진행 작업을 유예 종료한 뒤 시점을 고정한다. 복구 범위는 해당 checkpoint까지다.
- 복원 대상의 DB·파일·topic·group·connector는 원본과 분리한다. 원본 live offset/history를 초기화하거나 DB만 과거로 돌리고 최신 소비 위치를 그대로 붙이지 않는다. 복원 DB의 Outbox/Inbox를 기준으로 별도 namespace의 snapshot/replay 범위와 소비 시작점을 명시한다.
- WSL 자원이 부족하면 전용 시험 환경을 순차 기동하는 방식으로 조정한다. 기존 환경의 데이터/volume을 제거해서 공간을 확보하지 않는다. 실행 방식 조정과 그 영향을 원장에 기록한다.
- 복원 실패 시 원본 환경을 계속 보존하고 실패한 새 복원 대상에서 중단한다. checksum/manifest가 맞지 않는 checkpoint는 적용을 거부한다. checkpoint/증거는 보존하고 새로 생성한 M05 소유 시험 자료만 검증 후 정리한다.
- M04에서 남긴 READ HTTP/DTO 오류의 즉시 중단 가드 미연결은 실험 안전 중단 보강에 포함한다. 기존 일회성 로그인 대기 초과와 reader 준비 실패는 기동/readiness 과정에서 재현·오류 분류를 확인하며 원인 미확정 상태를 해결됐다고 바꾸지 않는다. 인증 검사를 우회하거나 무한 재시도로 통과시키지 않는다.
- 정상 경로가 바뀌면 영향 회귀와 소스/기존 실측본의 차이를 기록한다. 이번 단계에서 새로운 성능 개선율을 산출한다고 약속하지 않는다.

## 완료 기준

1. 정상 종료/강제 종료/DB 장애/broker 중단 기동/한도 동작이 기대 계약과 일치하고, 정상 복구 대상이 관찰 한도 안에 완료된다.
2. 정지 checkpoint를 분리된 대상에 복원해 요청·소유권·활성 snapshot·실제 PDF 크기/SHA가 일치하고 새 요청1건까지 완료한다.
3. 원본 재무 값/828개 미확인 격리를 보존하고 기존 volume/offset/history를 초기화·덮어쓰기하지 않았음을 대조한다. 시스템의 자연스러운 위치 진행과 강제 reset을 구분한다.
4. 수정 관련 회귀·독립 검토와 필요한 보강을 마치고 실행 절차·원자료·3줄 사례·컨텍스트를 갱신한다. 관측하지 못한 항목은 N/A/미완료 사유로 남긴다.
