# ADR 0003: 원장은 MySQL에 두고 상태 Redis는 기본 비활성화한다

- 상태: 상태 캐시 구현·장애 검증을 유지하되 기본 off.
- 근거: 2026-11-12 M04 실제 off/on/on/off 비교. 이후 운영 시험을 새 성능 실측으로 해석하지 않는다.

## 대상과 판단

검증된 원천 재무 값, 요청 수락, Outbox/Inbox, 작업·시도·관리 재개, 최종 파일 참조는 MySQL을 원장으로 유지한다. Redis에 먼저 성공했다고 응답한 뒤 DB에 나중에 쓰는 write-behind는 이 데이터의 복구·정확성 문제를 늘리므로 적용하지 않았다. 재계산할 수 있는 조회 결과만 캐시 후보로 삼았다.

상태 조회는 MySQL에서 소유권과 현재 버전을 먼저 확인한다. owner/request별 키와 TTL 2초, 정밀도를 보존하는 Lua 버전 비교를 적용했다. 별도 소비자 그룹이 상태 이벤트를 받으면 payload의 옛 상태를 바로 쓰지 않고 현재 DB를 읽어 재구성한다. 상태 Redis 장애는 짧은 timeout 뒤 DB로 조회하고, projector는 캐시 쓰기 성공 뒤 ACK하며 실패를 재시도한다. 인증 Redis와 연결/자원을 구분한다.

## 비교 결과와 채택하지 않은 이유

동일 소스·실제 재무 149,976행·20사용자·완료100요청·동시성10·warm30초/main120초로 off/on/on/off를 3회 반복했다. 각 모드 6회에서 P95 중앙값은 36.122→32.393ms, TPS 중앙값은 446.379→483.413이었다. 그러나 반복 범위가 겹치고 인접6쌍 중3쌍이 악화됐으며, 평균 SQL은 1→1.0975로 늘었다. 동시 cold100회는 소유권 확인을 포함해 SQL200회였다.

작은 절대 지연 차이와 변동, 별도 Redis/projector 운영 비용을 고려해 이 경로는 기본 off로 유지했다. 통계적 유의성을 입증한 결과가 아니며 전체 Redis 사용을 기각한 결론도 아니다. 인증·횟수 제한과 기존 Redis 경로의 용도는 별도다. 당시 원자료의 독립 재계산은 Git 제외 `perf/results/20261112-r07-m03-m04/v2-independent-analysis.json`에 있다.

## 장애와 보안 경계

상태 Redis의 중단·TTL 만료·시험 소유 키 소실은 DB 원장의 유실을 일으키지 않아야 한다. 타인 키와 삭제 사용자는 캐시에 데이터가 있어도 조회할 수 없어야 한다. `ReportStatusCacheIntegrationTest`, `StatusCacheFailureTest`, `PortfolioFaultMatrixTest`가 이 조건을 다루며 현재 실행 판정은 별도 원자료에 기록한다.

인증 Redis 전체 장애에서 인증을 우회하는 가용성, 캐시를 켠 모든 트래픽의 성능 개선, 보고서 생성 속도 개선은 이 결정의 검증 범위가 아니다. 상태 버전이 안전하더라도 원격 HTTP exactly-once를 보장하지 않는다.
