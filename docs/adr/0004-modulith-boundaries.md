# ADR 0004: 배포를 분리하기 전에 모듈 경계를 검증한다

- 결정일: 2026-11-15
- 상태: 채택. B01~B08 검증 결과는 별도 실행 자료로 관리한다.

## 문제

기존 계층별 패키지에는 다른 도메인의 Entity/Repository 참조, 공통 코드의 계정 역의존, 보고서의 재무·파일 테이블 직접 접근이 있었다. 이 상태에서 서버만 나누면 로컬 트랜잭션과 FK가 보장하던 조건을 원격 호출이 대신해야 한다. 실제 운영 요구 없이 배포·데이터베이스를 먼저 늘리는 비용도 크다.

## 결정

단일 Gradle·단일 Spring Boot·단일 MySQL을 유지하면서 Spring Modulith 1.4.14로 11개 모듈을 닫는다. 계정/인증은 identity, 원천 재무·적재는 finance, 맞춤 보고서의 수락·전달·실행·확정은 reporting, AI HTTP 전송은 aiintegration이 소유한다. 나머지 책임과 59개 테이블의 소유자는 [소유권 문서](../architecture/module-ownership.md)에 고정한다.

다른 모듈은 공개 API와 DTO·읽기 스냅샷을 사용한다. ID로 관계를 표현하고 목록은 배치 API로 전달한다. 전역 HTTP 경로·CORS·401/403 조립은 app에, 서명 키와 토큰 발급·검증은 identity에 둔다. 공개 API 내부 구현이나 JPA 타입을 노출하지 않는다. 관리 CLI는 읽기 전용 조립 API를 명시 등록해 웹 서버와 키 발급 없이 실행한다.

전체 `ApplicationModules.verify()`와 공개 타입 검사, 11개 STANDALONE 기동 시험으로 경계를 확인한다. 알려진 문자열 SQL 소유권 검사와 대표 실행의 SQL 관찰, 별도 최소 권한 계정 시험을 함께 사용한다. OPEN 모듈·전체 허용 목록·전체 의존 기동으로 위반을 숨기지 않는다.

요청/슬롯/Outbox 및 파일 메타/artifact/완료는 기존 로컬 트랜잭션을 유지한다. Debezium CDC를 유일한 durable relay로 사용하고 Modulith 이벤트 외부화를 중복 추가하지 않는다. 새 blob은 DB 정상 롤백 시 해당 객체만 보상 삭제한다. 업로드 직후 스트림 종료 실패도 보상 등록 범위에 포함한다.

## 대안과 비용

지금 독립 서버/DB로 추출하면 source 확보와 보존 예약, 계정 정지 전파, 파일 메타 확정과 보상, 재전달을 분산 실패 조건에서 다시 설계해야 한다. 현재 단계에서는 경계 검증과 같은 조건의 회귀·성능 비교를 우선한다. 단순 패키지 이동만으로는 문자열 SQL과 조회 호출 증가를 차단할 수 없어 별도 검증을 둔다.

공개 계약과 매핑 코드가 늘고 기존 join 일부가 여러 읽기로 바뀐다. 상태 조회는 계정 검사와 요청 조회를 분리해 기본 경로 SQL이 증가한다. 관심기업 기본 정보는 기업별 호출 대신 한 번의 배치 계약을 사용한다. 성능 개선을 가정하지 않고 같은 데이터·동시성·측정 창으로 전후 비용을 공개한다.

## 실제 서비스 추출 전 필요한 작업

1. AI 제공자의 멱등성·timeout·응답 계약과 운영 장애 정책을 확정한다. Inbox의 DB 멱등성은 외부 HTTP exactly-once가 아니다.
2. reporting 추출 시 source 버전 확보/보존, 별도 파일 서비스 실패 보상, 계정 상태 전파, 독립 DB 재전달을 검증한다.
3. identity 추출 시 공개키/JWKS·키 회전·토큰 폐기·계정 정지 전파 지연 및 자원 서버의 업무 권한 정책을 정한다.
4. 기존 72개 FK 중 모듈 간 16개와 교차 모듈 로컬 트랜잭션을 해소하고 삭제·참조 무결성 정책을 재검증한다.

단일 DataSource의 코드 규칙은 물리 접근 격리와 다르다. 정상 롤백 보상도 프로세스 사망이나 원격 삭제 장애에서 파일·DB 원자성을 보장하지 않는다. 실제 원격 S3·외부 AI 품질·다중 broker HA 및 독립 서비스 배포는 이번 결과에 포함하지 않는다.
